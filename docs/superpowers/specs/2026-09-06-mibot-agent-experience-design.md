# Mibot Agent 体验层设计：双人格（桌宠 / 助手）+ 记忆 + Skill + MCP

- 日期：2026-09-06
- 状态：**草案，待评审**（未实现；归属 SF32 侧蓝图，与 spec v2 §11 同层）
- 上游依据：《规范》§1/§2.1/§4/§5；spec v2（三平面归属、AI 网关、运动安全）
- 与 ESP32 交付物（本仓库）的关系：见 §8——**零新增协议帧**，仅建议 M2 增补一个 ToF 接近事件

## 1. 定位与假设

最终形态是 **AI 桌宠**：平时是"不说人话"的宠物（叫声/动作/表情表达），可切换为"说人话"的 Agent（语音助手 + 工具执行）。本设计覆盖 Agent 内核的改进逻辑：模式架构、记忆、Skill、MCP、行为循环。

**假设（评审时逐条确认）**：
- A1 SF32 侧有 LCD（表情）、扬声器、麦克风；宠物音效包存 SF32 本地（ESP32 无喇叭，音频链路本来就是回到 SF32 播放）
- A2 "触摸"感知用 ToF 接近度近似（ESP32 无触摸传感器）；"有人靠近/离开"是宠物感知的核心输入
- A3 桌宠长时间无人交互应自主活动（这是"桌宠感"的来源），但运动永远经 ESP32 安全栈
- A4 云端不可用时桌宠模式必须仍可用（降级为本地行为）；Agent 模式依赖云端

## 2. 双人格模式：方案对比与推荐

| 方案 | 结构 | 优点 | 缺点 |
|---|---|---|---|
| **A. 单内核双人格包（推荐）** | 一个 AgentLoop；人格 = 人格包（system prompt + 输出通道映射 + 工具/技能子集 + 行为策略参数） | 一套记忆/技能/循环；模式可平滑混合（宠物偶尔说人话）；实现量最小 | prompt 纪律要求高，两模式行为需测试防串味 |
| B. 双 Agent 实例 | 桌宠 Agent 与助手 Agent 各自独立上下文与循环 | 隔离彻底 | 记忆/技能双份基础设施；切换 = 上下文交接；SF32 资源紧张 |
| C. 规则桌宠 + LLM 点缀 | 宠物 = 本地规则 FSM，LLM 只偶尔生成一句话 | 最便宜、断云最强 | "智能感"天花板低；不满足双模式目标 |

**推荐 A，且 C 作为 A 的断云降级层**（人格包里预置一份"无云端行为策略"，云端失联自动降档，符合《规范》§5.2）。

### 2.1 人格包（PersonaPack）结构

```json
{
  "id": "pet_v1",                       // pet_v1 / agent_v1
  "system_prompt": "……",               // 人设 + 行为规则 + 词汇表索引
  "output_channel": "performance",       // performance=结构化表演指令 | speech=语音/文本
  "skills_active": ["*"],                // 技能激活集（§5）
  "tools_allowed": ["robot.*"],          // agent_v1 额外放开 MCP/云端工具
  "policy": {                            // 桌宠行为策略
    "llm_tier": "fast",                  // 策略调用用便宜快模型（NVS 可配第二模型）
    "min_policy_interval_ms": 30000,     // 无事件时的最小策略调用间隔（省钱）
    "autonomy": { "idle_wander": true, "attention_seek": true },
    "offline_fallback": "rule_fsm"       // 断云 → 方案 C 层
  },
  "vocabulary": [ ... ]                  // 宠物语词汇表（§7）：音效/表情/动作组合
}
```

### 2.2 模式切换（ModeManager）

- **显式**：语音指令（"说人话"/"安静"——两个模式各自的关键词都要在 ASR 关键词表里）、App/串口开关、定时段（如工作时间=安静桌宠，晚上=助手）
- **隐式**：云端失联 → 自动降为宠物模式（离线层）；长时间无交互 → 宠物自主进入低活动状态
- **LLM 发起的切换**：`switch_mode` 是注册工具；策略文件决定哪些触发需用户确认（默认：切到助手需语音确认一次，切回宠物随时可）
- **防抖**：模式切换带迟滞（冷却 60s），避免串味抖动；切换事件本身写入情景记忆

## 3. Agent 内核改进：双循环

**反应循环（无 LLM，高频）**：
- 输入：ToF 接近事件（ESP32 EVENT）、语音活动/唤醒词、定时器（需求衰减 tick）、MCP 事件推送、机器人 EVENT（edge_detected/motor_stall——宠物对障碍物做出"吓一跳"表演）
- 职责：打断（barge-in 优先级最高）、模式切换触发、需求状态数值衰减、行为硬中断
- 边界不变：一切运动安全仍在 ESP32 本地（这层只是感知与调度，不碰安全权威）

**慎思循环（LLM，事件/周期驱动）**：
- 助手模式：现有请求-响应 loop（多轮 ≤8，工具预算沿用《规范》第 4 章）
- 桌宠模式：**策略调用**——把压缩的状态向量（心情/需求/最近事件/ToF/电量/时段）发给快速模型，问题为"下一步表演什么"，答案为词汇表中的行为选择（§7）；无事件时最低间隔 30s；相同情境允许策略缓存复用（连续独处时重复"趴着"无需重复调用）
- 两循环通过统一事件队列交互；LCD 表情永远反映真实状态（延续《规范》§8.2 步骤 5 的要求）

## 4. 记忆体系（四层 + 固化）

| 层 | 内容 | 载体 | 生命周期 |
|---|---|---|---|
| 工作记忆 | 当前回合上下文 + 当前心情/正在做的行为 | RAM（AgentContext 扩展） | 会话 |
| 情景记忆 | 交互事件流水（时间/模态/标签/一句话摘要）：被摸头、有人敲桌、玩了接球 | SF32 文件系统 JSONL 环形缓冲 | 容量上限（如 500 条），按重要性保留 |
| 语义记忆 | 关于用户与世界的稳定事实："主人叫 X""摸头=开心""下午 3 点主人喝咖啡" | 单个 JSON 文档（≤200 条事实，含置信度） | LLM 固化时合并/冲突以最新+高置信为准 |
| 程序性记忆 | 技能（§5），含"学会的新把戏" | 技能包文件 | 持久 |

**情感/需求状态（桌宠感的核心，横切四层）**：
- 心情向量（valence/arousal/energy）+ 亲密度（bond）+ 需求（无聊/想玩/电量）
- 更新：规则（互动+固定增量）+ LLM 在回合结束时的判断（结构化输出，不打断对话）
- 用途：驱动桌宠自主行为选择（无聊→主动邀玩；亲密度高→更黏人）；对用户可见（LCD 表情/耳朵角度），**状态演化即使无命令也在发生**

**记忆固化（consolidation，"睡觉做梦"隐喻）**：
- 触发：空闲（如夜间/连续 2h 无交互）或每 N 次交互
- 过程：LLM 读最近情景摘要 → 提炼/合并语义事实 → 标记情景条目"已固化"（低重要性者可淘汰）
- 成本控制：批量低频调用，走快速模型 tier

**检索进 prompt**：每次循环注入 = 人格 prompt + 语义事实 Top-K（标签匹配 × 新近度 × 重要度评分，**不用向量库**——SF32 闪存/算力约束下的明确取舍，升级路径：若后续可用小型嵌入模型再换）+ 最近 N 条情景 + 当前情感状态。总预算对齐 spec v1 的 8KB 工具预算同级。

**隐私与遗忘**：记忆全部存 SF32 本地；仅派生事实经 ESP32 网关上行；"忘记我"命令按层擦除（语义→情景→情感重置）。

## 5. Skill 体系改进：行为技能统一注册表

现有定义（spec v2）：Skill = prompt 片段 + 工具组。桌宠需要把它升级为**行为技能**：

```yaml
skill: play_fetch
type: interactive            # interactive(互动) / habit(习惯) / performance(表演) / utility(工具)
triggers: ["扔球", "接球", "ball_thrown_event"]
preconditions: { motion_state: [STANDBY], mood_energy: ">0.4" }
prompt_fragment: "……接球规则……"
vocab: ["excited_bark", "fetch_pose", "happy_wiggle"]   # 用到的宠物语词条（§7）
tools: [robot.move, robot.set_arm_pose]
safety_class: motion          # motion 类技能受 ESP32 限幅/TTL 约束，写明参数上限
completion: { event: "robot.ack:completed", timeout_ms: 8000 }
```

- **注册表元数据进 prompt（渐进披露）**：system prompt 只放技能名+一句话描述，选中才加载完整片段——适配 prompt 预算
- **来源**：内置 + 用户自编（YAML 包）+ **学会的技能**（程序性记忆的形成）：LLM 把一次成功的临时行为序列提议固化为技能草稿 → 用户确认 → 存为技能包（"学会新把戏"是桌宠的核心体验，也是记忆层与技能层的汇合点）
- **双模式同源**：桌宠模式下技能=行为词汇的编排；助手模式下技能=工具编排。同一注册表、两套激活集（人格包 `skills_active`）

## 6. MCP 使用策略

1. **MCP 工具 = 行为素材**：注册的远程工具（智能家居/日历/音乐等）对两种模式同等可见。桌宠可以用它们表演：日历临近事件 → 宠物叼来提醒（碰瓷式拱手）；日落事件 → 触发"开灯"技能作为行为步骤。**行为编排中的一步可以是一次工具调用**——统一了"表演"与"做事"。
2. **预算纪律（强化现有约束）**：工具 schema 只列名进 prompt；每服务器工具数上限 + 每回合调用预算（沿用 ≤8KB/32 工具）；**异步带超时**——桌宠模式绝不允许被死掉的 MCP 服务器卡住（超时→降级为纯本地行为并记 EVENT）
3. **Schema 缓存**：工具清单缓存于 SF32，带刷新节流（重连时刷新，不逐次拉取）
4. **（远期）桌宠自身作为 MCP server**：手机/PC 客户端查询宠物状态、投喂互动——新增攻击面，默认关闭，M7+ 再议

## 7. 宠物语：结构化表演指令（输出通道映射）

桌宠模式的 LLM 输出不是文本，是**表演指令**（performance）：

```json
{"emote":"happy","sound":"excited_bark_02","motion":{"type":"approach","ttl_ms":1500,"speed_mm_s":60},"lcd":"excited_01","say":null}
```

- `sound`：SF32 本地音效包索引（**零 TTS 成本、零延迟**；音效包 = wav/opus 文件 + 触发标签，用户可换"皮肤"）
- `motion`：全部映射为《规范》§4.2 的 robot.* COMMAND（小 TTL、保守限幅）——**宠物自主性的安全边界与用户命令完全相同**，ESP32 不感知"这是宠物自发还是主人指令"
- `lcd`：表情帧索引（与真实状态同步，延续 §8.2 步骤 5）
- `say`：桌宠人格包可配"偶尔说人话"（触发词命中或概率阈值时填 TTS 文本）——这是两模式的**连续谱**而非硬边界，由人格包参数控制
- 助手模式的输出通道 = speech（现有设计），`motion` 字段仍可用（说话时配合动作）

## 8. 对 ESP32 侧（本仓库）的影响

**零新增协议帧**——全部复用《规范》既有契约：robot.* COMMAND（宠物动作）、EVENT(0x20)（安全/异常事件）、TELEMETRY(0x21)（感知源：motion_state/ToF/电量）、AUDIO_UP/DOWN、AI_REQUEST/RESPONSE。

唯一建议：**M2 的 ToF 任务增补"接近事件"**——ToF 距离越过阈值（如 <150mm 稳定 500ms）时上报 `EVENT proximity_changed(near/far)`（去抖后低频，不刷屏）。这是宠物"感知到有人来了"的核心输入，实现成本约 20 行，语义上属于 EVENT 的自然扩展，不影响既有 DoD。

依赖时序：本设计可在 M3（运动命令可用）后开始 P0/P1（纯 SF32 侧 + 现有帧）；完整桌宠体验（自主走动表演）需 M3；带 ToF 反应的表演需 M2。

## 9. 落地顺序（SF32 侧，P0-P3）

| 阶段 | 内容 | 依赖 |
|---|---|---|
| P0 | 人格包框架 + ModeManager + 输出通道映射（performance 结构先只用 emote/lcd/say，motion 置空） | 无（可与 M2/M3 并行开发） |
| P1 | 情感/需求状态 + 情景记忆 + 桌宠策略循环（快速模型 tier） | P0 |
| P2 | 行为技能注册表 + 记忆固化 + 学会技能流程 + 音效包 | P1，M3（robot.* 可执行） |
| P3 | MCP 集成（异步预算纪律）+ 接近事件表演 + 断网规则 FSM 降级层 | P2，M2（ToF 接近事件） |

## 10. 风险与开放问题

**风险**：
- prompt 串味（宠物人格漏进助手模式）→ 人格包隔离测试用例 + 切换迟滞 + 关键词路由在前
- 策略调用成本失控 → min_policy_interval + 策略缓存 + 快速模型 tier + 事件驱动优先于周期驱动
- 记忆固化产生错误事实 → 固化输出带置信度，低置信不注入；用户可查看/编辑记忆（串口/App 命令）
- SF32 存储与算力 → 结构化检索而非向量库；环形缓冲硬上限

**开放问题（请评审确认）**：
1. 假设 A1/A2 是否成立（SF32 扬声器/LCD 型号；触摸是否只靠 ToF 近似——要不要加一枚触摸/按键？）
2. "偶尔说人话"是可配置连续谱（§7 say 字段）还是严格二模式？
3. 记忆容量预算是否可接受（情景 500 条 + 语义 200 条，~1-2MB flash）？
4. `switch_mode` 哪些方向需要用户确认？
5. ToF 接近事件（§8）是否同意列入 M2 计划？
